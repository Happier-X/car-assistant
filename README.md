# 车机助手 · Car Assistant

## 未发布：BLE 方向诊断（连接诊断增强）

**前提：本应用装在车机上**（2024 款雪佛兰科鲁泽 MyLink / Android 10）。要诊断的是「车机发出的 BLE 广播，手机（小米 15，CarWith）能不能扫到」，不是「车机能不能扫到周围设备」。车机自己在扫描时基本收不到自己刚发出的广播（同一蓝牙控制器），偶发捕获不可靠、不能作为证据，还会因为同时广播 + 扫描降低广播成功率。因此本机扫描只覆盖接收方向，永远不能证明手机能扫到车机。

诊断结论按方向拆开，缺失证据一律记「未知」，不合并成一句「BLE 正常 / 异常」：

- **发送方向（车机→手机）**：依据只有本应用广播启动回调 + 手机侧登记（用户自述）。
- **接收方向（设备→车机）**：依据只有本机限时扫描结果。

手机侧登记在诊断页：结果（扫到 / 没扫到 / 扫到但载荷不是 CA1 / 未测试）、手机型号、扫描工具、观察时间、备注。可随时修改或清除；界面与报告都标注「用户自述，非系统自动采集」，本应用没有连接手机、没有读手机日志，不会把登记升级为客观事实。备注按不可信纯文本处理（单行化、去控制字符、限 200 字、不执行、不当 HTML），默认导出会隐藏 MAC、邮箱与疑似 VIN。

诊断页新增手动 **15 秒 BLE 扫描**（可停止，最多 100 条），离页/后台请求停止本应用扫描，失败保留数字码/异常类型并阻止重入。先授予精确位置权限并检查定位、蓝牙开关，再手动开始；不自动开蓝牙、连接设备或开机扫描。结果包含 RSSI、接收时间/开机单调时钟、UUID、厂商与 Service Data、平台原始记录、API26+ 可连接性。重复观察不代表不同设备；截断上限见界面，密集回调超过处理队列上限时丢弃并计数（不代表未广播）。Android 的 `ScanResult.scanRecord` 是广播与扫描响应的组合，不能据此独立分离 scan response；CarLink 内部广告内容未知，须另一设备观察验证。

**使用流程：**「车机诊断」→ 如需接收方向证据，在「BLE 限时扫描」授权并扫描 → 如需发送方向证据，点「开始 BLE 测试广播（30 秒）」后用手机 nRF Connect 找 Service Data UUID `9cb329d0-536c-4f32-8ea4-5b9021f67a10`、载荷 `CA1`，再回到「手机侧观察登记」记录结果 →「平板 / 车机报告导入对比」分别选择 A/B 的 TXT/日志（可本地改名）→ 查看阶段证据、时间和原始行号 →「保存扫描、方向结论与对比 TXT」。默认文件及普通报告/局域网页只导出扫描统计、方向结论、脱敏登记与阶段摘要，不含扫描载荷、导入原文、源路径或自定义名称。只有显式勾选才向用户选择的文件保存扫描载荷；这些字节可能包含标识，需自行保管。保存前停止扫描并固定快照；普通报告仍须主动点击下方「生成最新诊断报告」，可继续复制、分享或从原网页下载。

导入仅读取系统文件选择器选中的文件，不覆盖原文件。单份 512 KiB / 12000 行 / 单行 8192 字符，UTF-8 或带 BOM 的 UTF-16；未知格式保留本地原文、说明无法自动解析，不承诺支持 nRF 导出的所有格式。原文可分页查看，仅保留在进程内；不要在共享屏幕展示私密内容。最多提取 500 条事件，达到上限明确提示。按原始行序保留多次广播、成功与后续断开；建组回调仅为请求受理，认证日志仅为交互证据，缺失阶段为未知。不同来源、无年份/跨天/时区不同不作绝对时钟或尝试因果对齐。对比是阶段证据覆盖差异及共有/独有线索，不将共有异常判为根因；建议仅供后续手动验证。

实现依据：[ScanResult 官方文档](https://developer.android.com/reference/android/bluetooth/le/ScanResult#getScanRecord())、[ScanRecord 字节定义](https://developer.android.com/reference/android/bluetooth/le/ScanRecord#getBytes())、[按 target 区分的蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)。保留 targetSdk28、版本 1.3.0 (6)、既有签名和 P2P 门禁。本增量没有操作车机或手机；权限拒绝、无线接收、厂商 ROM、后台清理与文件选择完整交互仍需真机验收。

`app/src/test` 提供实际解析、比较、输入限制和会话门禁测试；`BleDirectionTest` 覆盖方向结论（未知 / 扫到 / 没扫到 / 载荷不符 / 只有广播回调无手机侧登记 / 无回调下的没扫到 / 接收方向独立）与登记字段校验（单行化、去控制字符、限长、默认导出脱敏）。两个资源文件来自真实报告的最小事件摘录，已去 PID/活动实例标识，摘录行号不等于原文件行号。平板 2026-10-26 报告记录 19:57:53 投屏、19:58:09 断开及后续重新广播；车机 2026-10-24 报告只匹配三次广播回调。两份都有 `startAdvertising` 栈片段；当前车机旧样本没有 `mInterval` 行，不能把该字段写成这两份材料的共有结论。原始完整报告不入库；设置 `CAR_ASSISTANT_TABLET_REPORT` / `CAR_ASSISTANT_CAR_REPORT` 为本地文件路径后，可运行可选的完整材料一致性测试。常规测试不依赖私有文件。

## v1.3.0：车机诊断、BLE 广播与 Wi-Fi Direct

安装支持 root 与系统安装器；无障碍安装代点因无法可靠核对窗口内的目标 APK，默认关闭，无 root 时请在系统安装器手动确认。

新增 **Wi-Fi Direct 直连**：诊断页可查看支持、精确位置权限/定位开关、P2P 启用/发现/系统组状态，手动发现设备、选择连接或创建组。操作前须勾选可能影响热点/WiFi/CarLink 的提示，并查询当前共享状态；已有组、协商中或状态不明时拒绝另发操作。系统请求受理与实际成组分开显示，失败保留数字码/异常类型；设备名仅在本页用于选择，MAC 仅在进程内传给连接 API，报告不导出设备名/MAC/组名/密码/凭据。Android10+ 以 target28 所需精确位置权限和定位开关工作，不读取坐标；Android10 以下仅提供能力与系统设置入口。

公开 API 没有强制打开 P2P 的总开关，标准入口会尝试系统 WiFi/无线设置，厂商可能裁剪直连子菜单。P2P 组没有创建 App 的公开归属信息，因此本页不提供全局停止发现、取消协商或移除组；离页/后台只结束本页观察、注销 receiver 和关闭自己持有的 channel，系统请求可能继续，最后一个 channel 关闭也可能触发系统清理。不会自动断开手机热点或开机建组，不能保证无线资源互不影响；P2P 也不等于热点，不保证为现有 HTTP 服务提供可用地址。

诊断页增加 **BLE 蓝牙广播测试**：先刷新查看系统 BLE 特性、适配器/开关、多实例广播能力与 advertiser 接口，再手动开始最长 30 秒测试。仅 `onStartSuccess` 表示系统接受启动；失败显示 `ADVERTISE_FAILED_*` 数字/中文原因或异常类型，未知、蓝牙关闭、无权限与缺接口分别说明。可请求系统开启蓝牙或跳转标准设置；不会自动开启蓝牙、开机广播、扫描或建立连接。保持 targetSdk28，manifest 声明 `BLUETOOTH` / `BLUETOOTH_ADMIN`（不限制到 API30），新系统按旧 target 兼容规则调用并处理权限拒绝，不套用 target31 的迁移示例。

测试使用独立固定 Service Data UUID `9cb329d0-536c-4f32-8ea4-5b9021f67a10`、固定 3 字节 `CA1`（43 41 31），只放一次 UUID，不含名称/制造商标识/应用生成的唯一身份，低功耗、低发射功率、不可连接。离开诊断页、应用后台、蓝牙关闭与 ViewModel 释放会请求停止自身广播；停止 API 没有成功回调，异常会记录且阻止新测试，可重试停止。报告含能力、最近测试时间、回调结果/错误和停止记录，不含 MAC/连接凭据。蓝牙协议自身的无线地址由系统管理，本应用不采集或导出。另一设备需按 Service Data UUID 实扫验证收到，测试成功不代表 CarLink 兼容；原 CarLink 日志缺异常头，也不能证明硬件不支持。

主界面顶部「车机诊断」可查看系统/硬件、Android 版本、内存/存储与 WiFi 局域网 IP，以及只读 ADB、开发者配置状态。大字滚动显示，读取在后台进行；点击刷新重新采集。普通侧载应用无法确认实际 ADB 连接，配置开启不等于能连接。Android 10 没有 Android 11 的标准无线配对功能，MyLink 也可能裁剪设置入口；按钮仅尝试标准开发者页面、关于页和设置兜底，不强开 ADB、不调用 root 或隐藏工厂页，不保证车辆数据可读。

## 一、为什么这个需求比看起来难

「开机开 WiFi + 启动 App」听起来是两行代码的事，但 Android 从 9 到 14 一路收紧权限，
到车机上（ROM 千奇百怪、没有 GMS、Android 版本跨度大）就变成了一个**多策略降级**问题。

### 难点 1：Android 10 起，普通 App 无法打开 WiFi

| Android 版本 | `setWifiEnabled()` 的行为 |
|---|---|
| ≤ 9 (API 28) | 正常可用 |
| 10 (API 29) | **targetSdk ≥ 29 时直接返回 false** |
| 10+ | 引入「软开关」，设置页开关 ≠ 射频真实状态 |
| 12+ | 部分车机 ROM 把 `WifiManager` 的 set 接口整体封死 |

**本项目的对策：`targetSdk = 28`。**

这不是偷懒，而是**刻意的设计决策**。车机是纯侧载场景（不进 Google Play），
不受 targetSdk 政策约束，因此可以用这个「后门」让 `setWifiEnabled()` 在
Android 10/11/12/13 上继续生效 —— 这是无 root 情况下唯一能真正静默开 WiFi 的途径。

### 难点 2：Android 10 起，后台无法启动 Activity

开机自动拉起 App 恰好是最典型的「后台启动」场景，会被系统静默丢弃，
logcat 里能看到 `Background activity start ... blocked`。

### 难点 3：亿连的包名未知

不同版本、不同渠道的亿连包名不一样，硬编码必然失效。

**本项目的对策：做成应用扫描器**，列出车机上所有已安装应用（含系统预装、
无 launcher 入口的隐藏应用）供用户点选，见「启动项」页。

## 二、解决方案：多级降级链

核心思路：**不赌单一方案**。按「成功率 × 侵入性」排序，逐级尝试，
**每级执行后都真实复查状态，成功即停止，绝不盲目往下走、也绝不虚报成功。**

### WiFi 开启策略链

| 序 | 策略 | 前置条件 | 说明 |
|---|---|---|---|
| S1 | `setWifiEnabled(true)` | targetSdk < 29 ✅ | 静默、无弹窗，首选 |
| S2 | 反射隐藏接口 | 部分 ROM 需要 | 绕过 ROM 的封装检查 |
| S3 | `su -c "svc wifi enable"` | root | 最经典的 root 方式 |
| S4 | `su -c "cmd wifi set-wifi-enabled enabled"` | root | Android 10+ 新命令 |
| S5 | `Settings.Global.WIFI_ON = 1` | WRITE_SECURE_SETTINGS | adb 可授予 |
| S6 | 无障碍服务代点设置页开关 | 无障碍服务 | 最终兜底 |

### 应用启动策略链

| 序 | 策略 | 前置条件 | 说明 |
|---|---|---|---|
| A1 | `startActivity` + NEW_TASK | 系统未拦截 | 最干净 |
| A2 | `su -c "am start -n pkg/cls"` | root | |
| A3 | `su -c "am start --user 0 ..."` | root + 多用户 | 车机 profile 场景 |
| A4 | `su -c "monkey -p pkg ..."` | root | 不依赖 Activity 名，最鲁棒 |
| A5 | 无障碍服务 `startActivity` | 无障碍服务 | **不受后台启动限制** |
| A6 | 全屏 Intent 通知 | — | 提示用户一键打开 |

> **为什么无障碍服务是最强兜底**：
> `AccessibilityService.startActivity()` 不受后台启动限制约束，
> 这是 Android 10+ 上无 root 拉起应用最可靠的途径。
> 它同时还能代点 WiFi 开关，一举两得。

### 应用安装策略链（v1.3.0 新增）

| 序 | 策略 | 前置条件 | 说明 |
|----|------|---------|------|
| I1 | `pm install -r -t <path>` | root | 完全静默、无弹窗；目标版本更低时自动补 `-d` 允许降级 |
| I2 | `pm install --user 0 -r -t <path>` | root | 多用户 / 分身场景 |
| I3 | FileProvider + 系统安装器 | 允许「安装未知应用」 | 无 root 时的主力路径，需用户点一次「安装」 |
| I4 | 无障碍服务代点安装确认 | 默认关闭 | 无法可靠核对目标 APK，使用系统安装器人工确认 |

**这条链和另外两条最大的区别：结果有三种，而不是「成 / 不成」。**
无 root 的 Android 8+ 上每个包都必须由用户在系统安装器里点一次「安装」，
所以「我们已经调起安装器」和「包真的装上了」必须分开说，否则就是在虚报成功：

| 结果 | 判定方式 |
|------|---------|
| 已安装 | PackageManager 复查通过：包在系统里，且版本不低于目标版本 |
| 已调起安装器但未确认 | 安装器起来了但用户没点完 —— 既不算成功，也不算失败 |
| 失败 | root 未成功且系统安装器无法调起，逐级原因见日志页 |

> **为什么 root 路径要先暂存到 `/data/local/tmp`**：
> `pm install` 本质是让 system_server 去打开这个 APK 文件，而 App 私有目录
> （/data/data/... 与应用专属外部目录）system 用户读不到，会直接报错。
> 所以先 `cp` + `chmod 644` 再安装，装完清理。

### APK 获取：手机推送（主路径）+ 直链下载（备用）+ 本地/U 盘（兜底）

**手机推送**是本项目的主路径：车机端内置一个极简 HTTP 服务，手机浏览器直接上传 APK，
**手机端不需要安装任何 App**。

| 步骤 | 在哪 | 做什么 |
|------|------|--------|
| 1 | 车机 | 「管理 → 安装下载」→「开启手机推送」，页面大字号显示 `http://192.168.x.x:8080`（可点击复制） |
| 2 | 手机 | 连同一个 WiFi / 手机热点，浏览器打开上面的地址 |
| 3 | 手机 | 选 APK → 点「推送到车机」，页面显示上传进度 |
| 4 | 车机 | 收完自动走安装链；无 root 时在车机屏幕上点一次「安装」 |
| 5 | 车机 | 结果区如实显示：已安装 / 已调起安装器未确认 / 失败 |

> **一次性前置条件（很重要）**：
> 1. 车机需要**先在车机 WiFi 设置里手动连接一次手机热点并保存**。之后开机时
>    「自动开 WiFi」才会自动重连到这个热点；只打开 WiFi 射频是不会自己连上的。
> 2. 手机热点要一直开着，手机与车机处于同一网段（部分手机热点隔离或防火墙会阻止访问，需真机验证）。
> 3. 如果车机没连上热点、拿不到 IP，页面会显示「WiFi 已开但未连接手机热点，推送暂不可用」，
>    此时改用「本机 / U 盘 APK」安装；连上热点后推送地址会自动出现。

服务端约束（都是刻意的）：

- 只 bind 到局域网 IPv4（site-local），**不监听 `0.0.0.0`**，外部网络没有入口
- 只有 `GET /`（上传页）、`GET /health`、`POST|PUT /upload` 三个路由，没有远程执行能力
- 上传目录固定为应用专属目录 `apk/`，**不接受任何目标路径参数**；
  文件名会剥掉目录、清掉 `..`、只留安全字符并强制 `.apk` 后缀
- 单文件上限 512 MB、并发上限 4，超出直接返回 413 / 503
- 按 `Content-Length` 逐字节校验；上传中断会删除不完整分片，并如实报告「已收 x / y 字节」
- 端口默认 8080，被占用时自动尝试 8081~8089，实际端口写在车机页面和日志里

**直链下载**保留为次要入口（有些时候手上只有链接）：系统 `HttpURLConnection` 流式写盘
（不引入 OkHttp / DownloadManager），有百分比 + 速率、可取消、按 `Content-Length` 校验、
支持断点续传；地址会原样展示在确认弹窗里，下载完成后不会自动安装。

**本机 / U 盘 APK** 是推送失败时的兜底：扫描内部存储（`/sdcard`）与常见 U 盘挂载点
（`/mnt/usb*`、`/mnt/media_rw`、`/storage/*`），用 `getPackageArchiveInfo`
读出应用名 / 包名 / 版本 / 大小后点选安装。读不到的目录只记一条日志，不影响整轮扫描。

## 五、构建与安装

### 环境要求

- JDK 17+（Android Studio 自带的 JBR 即可）
- Android SDK（compileSdk 37 平台）

### 构建

```bash
# Windows
gradlew.bat :app:assembleDebug

# Linux / macOS
./gradlew :app:assembleDebug
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

### 安装到车机

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

车机没开 USB 调试的话，可以先把 APK 拷到 U 盘，用车机的文件管理器安装。

### 安装后必做（重要）

**第一步：授予 WRITE_SECURE_SETTINGS。**

这是无 root 情况下开 WiFi 的关键后路。用 adb 执行一次即可（重启不失效）：

```bash
adb shell pm grant com.carassistant android.permission.WRITE_SECURE_SETTINGS
```

**第二步：开启无障碍服务。**

在 App 里点「设置 → 开启无障碍服务」，或手动进入
`系统设置 → 无障碍 → 已安装的服务 → 车机助手（启动兜底）`。

它的作用：
1. 静默开 WiFi 失败时，自动点击设置页里的 WiFi 开关
2. 后台启动 App 被系统拦截时，代为启动（不受后台启动限制）

**第三步：加入电池优化白名单。**

避免流程执行到一半被系统冻结。

**第四步：在「启动项」页添加亿连。**

点「添加应用」→ 搜索「连」或「Link」→ 选中 → 它会被加到启动列表。

> 如果列表里找不到亿连，点「手动输入包名」直接填入。
> 想知道包名可以执行：`adb shell pm list packages | grep -i link`

**第五步：允许本应用安装未知来源的 APK。**

系统设置 → 应用 → 车机助手 → 安装未知应用（不同 ROM 路径略有差异；
也可以直接在 App 的「管理 → 安装下载」页点「去开启」跳过去）。
Android 8+ 这个开关是**按应用**授予的，不打开连系统安装器都不会工作。

**第六步（可选）：授予存储读取权限。**

要装的文件在车机内部存储或 U 盘上时，需要在「管理 → 安装下载」页授予存储权限
（Android 13+ 系统不再单独提供该权限，页面会如实提示哪些目录扫不到）：

```bash
adb shell pm grant com.carassistant android.permission.READ_EXTERNAL_STORAGE
```

## 七、常见问题

**Q：开机后 WiFi 没开，日志显示「静默方式全部失败」**

说明 `setWifiEnabled()` 在你的车型上被 ROM 封死了。检查：
1. 无障碍服务是否开启？（对应 S6 兜底）
2. 是否授予了 `WRITE_SECURE_SETTINGS`？（对应 S5）

**Q：日志显示「Root 权限：不可用」，但我的车机已经 root 了**

不同车机的 `su` 位置和参数不同。项目里已探测 8 种常见组合
（`su -c` / `su 0` / `su root -c` / `/system/xbin/su` …）。
如果都不行，在首页点「重新检测 root」再试。日志里会显示具体试过哪些路径。

**Q：亿连启动了但又退到后台，被后面启动的 App 顶掉了**

多个 App 依次启动时，只有最后一个会留在前台。解决：
在「启动项」页把亿连**移到第一位**，并把它的延时设为 **「立即启动」**。

**Q：开机广播没触发流程**

车机开机流程千差万别。本项目监听了 7 种触发源：
`BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `QUICKBOOT_POWERON`（熄火不断电的车机）/
`MY_PACKAGE_REPLACED` / `POWER_CONNECTED` / `DOCK_EVENT` / `SCREEN_ON`。

如果都不触发，去「设置 → 触发时机」把**「屏幕点亮时」**也打开
（代价是每次亮屏都会执行一次，已做 20 秒去重）。

**Q：启动后出现「无法自动启动 亿连」的通知**

这是 A6 兜底：所有静默手段都被系统拦截了，至少给你一个一键打开的入口。
请开启无障碍服务（对应 A5），它不受后台启动限制。

**Q：安装时提示「已调起安装器，但还没装完」**

这是无 root 车机的正常现象：Android 8+ 强制要求用户在系统安装器里点一次「安装」。
在车上点完「安装」再回来看结果即可。想做到全程静默，只能让车机 root（对应 I1/I2）。

**Q：点「安装」后系统提示「应用未安装」**

常见原因：与原包签名不一致（原包来自别的渠道）、版本降级被拒
（本项目已自动补 `-d` 重试过一次）、APK 的 ABI 或最低系统版本与车机不匹配。
每一级的真实返回码都在日志页里，可以一键复制出来排查。

**Q：手机打不开车机显示的推送地址**

先确认手机和车机在**同一个局域网**（同一个 WiFi，或都连着同一个手机热点）。
再看车机「安装下载」页的状态：如果显示「推送不可用：车机当前没有拿到局域网 IP」，
说明车机 WiFi 没连上或者没分到地址 —— 这时用「本机 / U 盘 APK」安装。
个别车机 ROM 会限制入站连接，可以换一个端口（关掉再开，服务会自动尝试 8081~8089）
或检查系统里是否有网络防火墙类应用。

**Q：二维码扫不出来 / 手机识别很慢**

先确认二维码内容与地址文本完全一致（地址每次实时刷新，二维码会跟着变）。
扫码时把手机对准车机屏幕、保持 20~40cm 距离，避开强光反射；确认车机没有开启
护眼/反色模式（二维码为白底黑块，不跟随深色主题）。如果仍然扫不出来，
直接点地址复制或手动输入 —— 地址和二维码是等价的。

**Q：大文件（≥50MB）上传会不会断**

服务端是 64KB 缓冲的流式写盘，不做内存缓存，50~200MB 的包在局域网内一般没问题。
如果中途锁屏/切走浏览器，连接会断：车机会如实显示「已收到 x / y 字节」并删除不完整分片，
手机重新上传即可（浏览器不支持续传，这是浏览器的限制）。

**Q：推送完成后车机没有自动安装**

看车机「安装下载」页的结果横幅与日志页：如果提示「已调起安装器，但还没装完」，
说明系统安装器在等你在车机上点「安装」；如果提示需要开启「安装未知应用」，
按提示去开启后重新推送一次即可（已收到的 APK 也留在本机列表里，可直接点它安装）。

**Q：扫不到 U 盘里的 APK**

不同车机把 U 盘挂在 `/mnt/usb`、`/mnt/usbhost`、`/mnt/media_rw/XXXX-XXXX`、
`/storage/XXXX-XXXX` 等不同位置，本项目把这些位置都试了一遍，并把每个目录的
可读结果写进日志页（「扫描根目录 N 个 / 某目录不可读，跳过」）。
如果日志显示所有根目录都不可读，说明该 ROM 对外部存储限制较严：
可以改用「下载」区粘贴直链，或先用系统文件管理器把 APK 拷进车机内部存储。

## 八、安装与下载（v1.3.0 新增）

### 8.1 页面位置

安装能力并入「管理」页，做成「卸载应用 / 安装下载」两个二级页，没有新增第 6 个底部标签：
车机屏幕上 5 个标签已经排满，再加一个会把标签文字挤到读不出来；而「装应用 / 卸应用」
本来就是同一件事的两面。

「安装下载」页四块内容：

1. **安装环境自检**：未知来源授权 / 存储权限 / 无障碍服务 / root，缺哪项点哪项去开
2. **手机推送（推荐）**：一键开关 + 大字号的局域网地址（点击复制）+ 地址下方的二维码 +
   接收进度 + 最近一次上传的文件名 / 大小 / 来源 IP
3. **直链下载（备用）**：地址原样确认 → 进度、速率、取消、续传 → 下载完一键安装
4. **本机 / U 盘 APK**：扫描结果列表，点一下走同一条安装链

### 8.2 手机推送的实现与取舍

- **手写 `ServerSocket`，不引入 NanoHTTPD**：需求只有「一个静态页 + 一个流式上传接口」，
  自己写反而能把失败原因（缺 Content-Length、上传中断、落盘失败、端口被占用）说清楚。
- **二维码用 zxing core（唯一的第三方依赖例外）**：用户明确要求「扫码更方便」。
  手写 QR 编码器一旦有 bug，表现是「手机相机扫不出来」——只能在真机上发现、
  用户无法自助排查，所以这里正确性优先：`com.google.zxing:core:3.5.3` 是纯 Java、
  无传递依赖（jar 约 607 KB），R8 之后 release 只增加约 0.03 MB。
  二维码内容与页面上显示的地址字符串完全一致，地址变化（换 IP / 换端口）时自动重新生成；
  没有地址时显示「暂无推送地址」的占位提示，生成失败则降级为「请手输地址」，不会崩页面。
  交付前用 zxing 自己的解码器对 240/260/280/320px 的生成结果做过回读校验。
- **服务跑在 App 进程内，不迁到前台服务**：推送时用户就停在「安装下载」页，
  进程本身处于前台优先级；ViewModel 结束时 `onCleared` 会 `stop()` 真正释放端口。
  代价是「切到别的 App 后长时间挂着服务」不受支持 —— 当前场景（当场推、当场装）不需要。
- **不提供「静默接收后自动安装」**：上传完成只是进入安装链，无 root 时仍要用户在
  车机上点一次「安装」；这是 Android 8+ 的硬性要求，页面和车机端都会写明。


### 8.3 手机推送安装怎么用（完整流程）

**一次性前置条件**

1. 车机先连一次手机热点：车机「设置 → WLAN」→ 选手机热点 → 输入密码 → 连接并保存。
   本项目负责的是**开机把 WiFi 射频打开**，至于连哪个热点由系统记住的网络决定；
   没保存过热点的话，开 WiFi 也不会自动连上。
2. 手机热点保持开启，并确认车机和手机在同一网段（车机 IP 一般是 `192.168.x.x`，
   网关就是手机）。
3. 手机浏览器不需要装任何扩展/App。

**每次推送的流程**

1. 车机打开「管理 → 安装下载」，点「开启手机推送」；
2. 页面会显示当前 WiFi（SSID）、车机 IP、网关（手机），以及大字号地址
   `http://192.168.x.x:8080`（点一下即可复制）和它正下方的二维码；
3. 手机相机扫码（或手动打开 / 粘贴该地址），看到「车机助手 · 手机推送安装」页面；
4. 点「选择 APK 文件」→ 选中文件（页面会显示文件名和大小）→「推送到车机」；
5. 手机端能看到上传百分比，车机端同时显示接收进度与来源 IP；
6. 上传完成后车机自动进入安装链：有 root 走 I1/I2 静默安装，无 root 走系统安装器，
   需要你在车机屏幕上点一次「安装」；结果显示在车机页面和日志页。

**地址是实时读的**

- 每次展示、每次从后台回到 App，都会重新读一次已连接 WiFi（优先于默认网络）的 IPv4、SSID、网关，
  不使用启动时缓存的地址（车机每次开机从手机热点拿到的 DHCP 地址可能变化）；
- 注册了 `NetworkCallback`：IP 变化、网络恢复时自动刷新展示地址；
- 监听 socket 绑定 `0.0.0.0`（本机所有网卡），换 IP/换网不需要重启服务；
- 没有拿到 IP 时不会报错，而是进入「等待连接热点」状态，拿到 IP 后自动开始监听。

**端口与 SSID**

- 端口默认 8080，被占用时自动尝试 8081~8089，实际端口显示在页面和日志里；
- Android 8.1+ 没有定位权限时系统会隐藏 SSID，此时页面显示
  「已连接（SSID 被系统隐藏）」，但 IP 和推送功能不受影响（定位权限仅在用户使用 Wi-Fi Direct 时请求）。

**排错**

| 现象 | 先看什么 |
|------|---------|
| 手机打不开地址 | 手机与车机是否同一热点；车机页面是否显示 IP；换个端口重启服务试试 |
| 车机显示「等待连接热点」 | 车机 WiFi 是否已连接到手机热点（不是只开了射频）；热点是否开着 |
| 上传到一半失败 | 车机会提示已收字节数并删除分片；让手机保持亮屏、重新上传 |
| 上传成功但没装上 | 看结果横幅与日志页：多半是在等你在车机点「安装」，或缺「安装未知应用」授权 |

### 8.4 新增权限与组件

| 名称 | 用途 | 备注 |
|------|------|------|
| `INTERNET` | 手机推送的局域网 HTTP 服务（监听 socket）+ 直链下载 | 不涉及任何上报；推送只服务局域网客户端 |
| `REQUEST_INSTALL_PACKAGES` | 调起系统安装器（I3） | Android 8+ 还需用户在「安装未知应用」里单独授权 |
| `READ_EXTERNAL_STORAGE` | 扫描本机 / U 盘上的 APK | 本应用 targetSdk=28，走旧版存储模型，Android 10~12 仍有效 |
| `FileProvider`（`${applicationId}.fileprovider`） | 把 APK 以 content:// URI 交给系统安装器 | exported=false，授权只对当次 Intent 生效 |

下载目录是应用专属目录 `getExternalFilesDir(null)/apk`，不需要任何存储权限，
卸载 App 时随之清理。

### 8.5 界面上的知情门禁

- **下载前**：弹窗把下载地址**逐字**显示出来，用户确认后才开始下载
- **安装前**：弹窗显示应用名、包名、版本、大小，以及**来源地址或文件路径**，
  必须手动勾选「我确认来源可信，并了解安装未知来源 APK 的风险」才能点安装
- **解析不出包名**的文件直接禁用安装，不会出现「点了半天没反应」
- 无 root 时界面和日志都明确写「已调起安装器，等待你确认」，不会显示假的成功

## 九、设计取舍说明

几个刻意的选择，避免后来者困惑：

1. **`targetSdk = 28` 不是没升级，是故意锁的。** 见第一节难点 1。

2. **前台探测失败时乐观返回「已在前台」。** 车机上探测手段（root dumpsys /
   无障碍事件）都可能不可用。此时若返回 false，会触发所有降级策略白跑一遍，
   甚至把已经正常打开的 App 再重启一次。宁可漏报，不可误判。

3. **WiFi 失败不阻断 App 启动。** 用户核心诉求是「上车就能看到亿连」，
   WiFi 只是前置条件。失败也继续，并在报告里如实标注。

4. **流程去重窗口 20 秒。** 开机时会收到多个广播，不去重会连续拉起好几次 App。

5. **`START_NOT_STICKY`。** 服务被杀后不自动重启 —— 开机场景下重启只会造成重复执行。

6. **不使用 `applicationIdSuffix` 区分 debug/release。** 包名必须一致，
   否则 adb 授予的 `WRITE_SECURE_SETTINGS` 在 debug 包上不生效。

7. **不做「静默安装」的假象。** 没有 root 就是装不了静默包 —— 这是 Android 8+ 的硬性
   规定，写多少降级策略都绕不过去。所以安装结果被拆成三态（已安装 / 已调起安装器待确认 /
   失败），宁可让用户多点一次「安装」，也不显示一个假的绿色成功。

8. **不做应用市场。** 应用商店意味着服务端、审核、分发和灰度，与「侧载小工具」的定位
   完全不符；而且车机上真正要装的多半是官方渠道之外的安装包（亿连、车机版应用），
   用户自己拿到直链或 APK 文件反而更直接。所以这里只做「下载器 + 安装器」。

9. **下载器自己写，不引入 OkHttp / DownloadManager。** 见第二节：DownloadManager
   的失败语义被系统吞掉，而车机上最需要的恰恰是「到底怎么失败的」。自己写还能保持
   仅保留二维码编码这一第三方依赖例外。

10. **续传必须校验来源 URL。** 同名 `.part` 只在 URL 一致时才续传，否则会把两个不同
    APK 的字节拼在一起 —— 这种包签名必然校验失败，但报错信息会把人带偏很久。

11. **扫描不到就说扫不到。** U 盘挂载点在每个 ROM 上都不一样，权限也随 Android 版本变。
   所以扫描逻辑对每个根目录单独容错，把「哪些目录不可读」写进日志，
   而不是抛异常或者假装扫描成功。

12. **主路径从「粘贴直链」改成「手机推送」。** 车机上敲 URL 是最反人类的操作之一；
   而手机里那个 APK 本来就在用户手上。推送方案让手机端零安装（浏览器即可），
   车机端也只需要一个几百行的 `ServerSocket`。直链下载保留为备用入口，不删但降级展示。

13. **推送服务监听本机所有 IPv4 网卡并校验局域网来源，不做鉴权。** 车机在车里、局域网是临时的（手机热点/车载 WiFi），
   加账号体系只会让「手机打开就能传」这个卖点消失。安全边界靠三件事保证：
   校验客户端局域网来源、路由与目录都写死、文件名严格清洗。页面本身也会写明
   「仅在车机所在局域网内可见」。

14. **二维码用 zxing，是「零第三方依赖」的唯一例外。** 用户明确要求扫码，
   而手写 QR 编码器的 bug 只会在真机扫码时暴露、用户无法自助排查 ——
   正确性优先于体积。zxing core 无传递依赖，R8 后 release 只增加约 0.03 MB。
   地址文本仍然保留大字号 + 点击复制，扫码失败时用户还有手输这条退路。
